Open-source roadmap

VirtualGPU

Tune GPU kernels without a GPU.

VirtualGPU imitates a graphics card on your ordinary CPU. It cannot tell you how fast a kernel really is. It can tell you which of two kernels is faster, and why. That is the question people actually need answered when they optimize AI inference.

Runs on any CPU Uses zero GPU hours No reverse engineering Apache-2.0
The problem

Making AI faster needs GPUs, and there are not enough of them.

Every AI model runs on small GPU programs called kernels. Making those kernels faster is how inference gets cheaper. But to make a kernel faster, today you must try it on the real GPU, again and again.

💸

GPUs are scarce

They are expensive, often sold out, and many developers have none at all.

🎯

Wrong card in hand

You own one GPU, but your users run another. You cannot tune for a card you do not have.

⚔️

Compute is contested

Every hour spent testing kernels is an hour taken from training and serving models.

The big idea

We do not need the real speed. We need the winner.

Think of a wind tunnel. A scale model of a car in a wind tunnel will never tell you the car's top speed. But it tells you, cheaply and reliably, which body shape has less drag. Engineers use it to pick the shape, then build the real car once.

Very hard · we skip it

"This kernel takes 41.7 microseconds."

Getting the exact time right needs every secret detail of the chip. The vendor does not publish those details, and copying them would mean reverse engineering. Even existing research simulators that try this are hours slow and still off by large margins on new GPUs.

Much easier · our goal

"Kernel A beats kernel B, because B waits on memory."

To compare two kernels, small modeling mistakes affect both of them the same way, so they cancel out. Public specifications and our own measurements are enough.

Why the mistakes cancel

Two runners race on treadmills that both run 20% slow. Their times are wrong. The winner is still the winner.

On the real GPU
Kernel A
50 µs
Kernel B
70 µs
In VirtualGPU (every time is off by 20%)
Kernel A
60 µs
Kernel B
84 µs

Both say A wins by about 30%. That is the answer we need.

What you get

Give it your kernel. Get back a ranking.

Kernel authors usually write one kernel with dozens of settings (tile sizes, number of warps, pipeline depth) and must find the fastest setting for each GPU. Today that search runs on the real GPU. With VirtualGPU it runs on your laptop.

You give

kernel: matmul.py (Triton) settings: 36 candidates problem: M=2048, N=8192, K=4096 target: profiles/H100.json

No GPU attached. The target card is just a file.

➜

You get back

  • 1128×128×64, 8 warps, 4 stages
    compute-bound, full waves    fastest
  • 2128×64×64, 4 warps, 4 stages
    within noise of #1    can't tell
  • 364×128×32, 4 warps, 2 stages
    waits on memory: pipeline too shallow    +18%
  • …33 more, each with a reason

Then you test only the top few on a real GPU, instead of all 36. Or none at all, if you have no GPU.

How it works

Four parts, each with one job.

1
Like reading a recipe

Frontend

Reads your kernel and works out its structure: how big each tile of work is, how it moves data, how many tiles run in total.

2
Like a common language

Kernel IR

Writes that structure down in one neutral format, the same no matter which language or vendor the kernel came from.

3
Like a flight simulator

Performance model

Plays out the kernel on an imaginary GPU: tiles get scheduled onto cores, share memory bandwidth, wait, and finish.

4
Like a spec sheet

GPU profile

A small file that describes one GPU: public specs plus numbers we measured ourselves with tiny test programs.

Many languages, one simulator

Kernels are written in many languages. They all end up in the same place.

There are many ways to write a GPU kernel, and new ones keep appearing. We will not chase every one of them. They all compile down to a small number of public instruction formats, and we meet them there.

Built to be honest

When it is not sure, it says so.

Every measured number has some uncertainty. VirtualGPU reruns each comparison many times, each time nudging the GPU's numbers a little up or down. If kernel A wins every single time, it says so. If the winner flips, it refuses to guess.

A is faster
A wins 32 of 32 runs

A won every nudged run. Trust it.

Can't tell
A wins 19 of 32 runs

The winner flips. Too close to call. Measure on real hardware if it matters.

B is faster
A wins 0 of 32 runs

B won every nudged run. Trust it.

A tool that says "I don't know" when it doesn't know is one people can trust.

Why open source

One person with a GPU helps everyone without one.

To imitate a GPU, VirtualGPU needs that GPU's profile, measured once on the real card. That is a job the community can share. Anyone who owns a GPU runs our short test suite and shares the resulting file. From then on, everyone can optimize for that card from any CPU.

The roadmap

Prove it small, then grow it.

Each phase ends with a test that must pass before the next one starts. If the first test fails, we learn that early and cheaply.

Phase 0

Design

Done

Decide what to build, what not to build, and how to know whether it works.

Delivered

  • Design document and five component designs
  • A plan for testing ourselves honestly
  • A list of risks, each with a planned answer

Key choices

  • Relative speed, not absolute speed
  • Triton first, other languages later
  • Core in Rust, frontend in Python
Phase 1

Prove it on one GPU

Done

The make-or-break experiment. Take one ordinary matrix-multiply kernel written in Triton, with 36 settings, and run every setting both in VirtualGPU and on a real RTX 4070.

What we build

  • Test suite that measures a GPU's profile
  • Triton frontend
  • First performance model
  • Two simple rival predictors, to beat

What you can do after

  • Rank matrix-multiply settings for an RTX 4070 without touching it
  • See why each setting is fast or slow
Pass test: VirtualGPU's top 5 picks contain the real fastest setting, and it ranks clearly better than the simple rival predictors. If simple formulas do just as well, we stop and rethink.
Phase 2

Predict a GPU we did not tune on

Planned

The real promise: optimizing for a card you do not have. We freeze everything we built on the RTX 4070, then give VirtualGPU only the profile of a different GPU, an NVIDIA DGX Spark, and check its rankings there.

What we build

  • Profile for a second, different architecture
  • Support for newer data-copy hardware

What you can do after

  • Trust rankings for a GPU you have never run code on
Pass test: the same quality bar as Phase 1, on a GPU whose results we never looked at while building the model.
Phase 3

Open the doors

Planned

Turn the experiment into a tool people use every day.

What we build

  • Drop-in "autotune without a GPU" for Triton
  • A shared library of GPU profiles
  • Simple steps to measure and contribute your own GPU
  • Automatic checks for contributed profiles

What you can do after

  • Add one line to your Triton kernel and pick a target GPU from the library
  • Contribute your own GPU in minutes
Done when: someone outside the project tunes a kernel for a GPU they do not own, and the result holds up on the real card.
Phase 4

More kinds of kernels

Later

Matrix multiply is the start. Large language models also spend their time in attention and mixture-of-experts kernels.

What we build

  • Attention kernels
  • Mixture-of-experts kernels, which depend on how tokens are routed
  • Whole-model view: which kernel is the slowest link

What you can do after

  • Point at a full model and see which kernels hold it back
Phase 5

More languages, more GPUs

Later

Reach kernels that are not written in Triton, and GPUs that are not NVIDIA.

What we build

  • PTX frontend: covers CUDA, CUTLASS, TileLang and more in one go
  • AMD GPU support
  • Profiles for newer and data-center GPUs

What you can do after

  • Use VirtualGPU no matter how your kernel is written or which vendor you target

Clear limits

What VirtualGPU will not do.

Predict exact times

We rank kernels. Exact microseconds are out of scope on purpose.

Copy anyone's chip

We use public specifications and our own measurements only. No disassembling of vendor drivers, firmware or tools.

Replace the final check

It narrows hundreds of options to a few. The real GPU still has the last word when it is available.

Compute your results

It predicts speed, not outputs. Use your normal tests for correctness.

In one sentence

If VirtualGPU says kernel A beats kernel B, the real GPU agrees, and nobody had to use a GPU to find out.
