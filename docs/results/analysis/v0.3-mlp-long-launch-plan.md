# Long-launch MLP recapture plan

This post-hoc calibration plan covers Spark 1 GB10 (`sm_121`) and
Bifrost RTX 4070 (`sm_89`). The installed GB10 MLP curves are
provisional after the dispersion audit. Frozen v0.2 results stand.
The capture uses microbenchmark data only.
[GB10 acquisition audit](v0.3-mlp-repeat-plan.md#gb10-calibration-record)

## What to repeat

Use the registered `mlp` and `strided-mlp` grids in full. Preserve each
point's bytes in flight, active CTAs, per-CTA bytes, issue instruction,
unroll and pipeline depth, and segment and stride where applicable.
Repeat the existing `dram-bw` and `l2` active-SM read grids in the same
session on each GPU. Record the observed SM counts, keep the existing
load instructions, and preserve the reduction's read ceiling rule.
Collect five fresh processes per mode, with three warmups and 15 timed
samples per point. Run all four modes under one session ID per device
so the active-SM and MLP read ceilings share a measurement window.

## One launch of at least 1 ms per sample

| Path | Change for a longer launch |
| --- | --- |
| Cold contiguous DRAM MLP | Increase steady-state step count for `cp.async` or register-staged read iterations. Expand the source range and consume unique lines across the full launch. |
| Cold strided DRAM MLP | Increase the step count and source range, preserving segment width, stride and segment-phase traversal. Allow enough space for the existing half-buffer transfer limit. |
| Warm L2 MLP | Repeat the existing traversal in the resident 8 MiB working set. Keep cache priming outside the timed launch. |
| Active-SM read sweeps | Extend the unique DRAM read span or increase iterations over the existing warm L2 working set, as appropriate. Keep SM and CTA placement and the read instructions. |

Use up to 1 GiB contiguous and 2 GiB strided source allocations as the
initial provision, subject to available memory. Choose the per-point
step counts from a microbenchmark sizing pilot, using the fastest
observed duration to target at least 1.25 ms with whole steps. This
avoids oversizing slow low-CTA points. Prove the cold address schedule
has no wrap or repeated cache lines across CTAs, including prologue and
tail reads and non-power-of-two grid sizes. Provision more unique space
in the pilot if needed. If memory or the address geometry cannot
support a 1 ms single launch, stop and review the proposed schedule.
Pre-touch allocations before the capture. Prepare cold state with a
separate read-only eviction buffer of at least three times L2, outside
the CUDA event interval. The measured interval contains exactly one
kernel launch. Record the step count, allocation, measured footprint,
accounted transfer bytes and 15 raw CUDA event durations per point.
Any timed sample below 1 ms invalidates the collection.

## Freeze and capture

1. Before the sizing pilot, archive the current predictions for the
   registered grid, with the core and input profile digests, the
   prediction digest and UTC. The pilot determines transfer length
   only. Retain the pilot receipts separately. Before the acceptance
   sweeps, freeze the exact per-device step counts, geometry, binary
   and source revision, toolchain, commands, and the published shared
   dispersion checker, with SHA-256 and UTC. Any necessary schedule
   revision gets its own receipt before a new complete campaign.
2. Hold `flock /tmp/virtualgpu-gpu.lock` during each invocation. Check
   before and after for foreign GPU work. On RTX 4070, use the shared
   Windows quiet gate for 60 consecutive seconds below 5% GPU, decoder
   and encoder utilization, and inspect the process and engine logs
   for gaming, GameViewer and sustained video or 3D work. On GB10,
   also check for competing CPU and memory activity. Defer on
   contention and save the observations without touching other jobs.
3. Per invocation, use the existing thermal gate: at least 60 seconds
   of warmup, a difference of at most 0.5 C between adjacent 30-second
   temperature means, at most 1% between SM clock medians, and no
   thermal or power slowdown in either window. At the 20-minute limit,
   stop and retain the trace. Record driver, clock policy, SM and
   memory clocks where available, temperature, power, clock-event
   reasons and host activity. Record clock readings when clocks
   cannot be locked.

## Accept and reduce

Require all 15 finite positive samples and identical full point keys
across all five processes of each mode. Apply the published shared
checker to `gbps_samples`, counting the duplicate event durations only
for the 1 ms protocol check. Use these three limits:

| Check | Maximum share above the point threshold |
| --- | ---: |
| Within-process IQR/median greater than 10% | 5% per process |
| Within-process max/min greater than 1.5 | 15% per process |
| Cross-process range of point medians relative to their median greater than 10% | 5% per mode |

Archive raw samples, point keys, gate results, telemetry, failed
attempts and SHA-256 receipts. Any failed check rejects the device's
campaign as a whole. For an accepted campaign, use the median of the
five process medians at every point. Publish their min and max and
archive pooled 75-sample statistics as descriptive data. Recompute the
two read ceiling scalars from the matching same-session active-SM read
endpoints and MLP peaks, retaining the existing maximum rule. Publish
the campaign and comparison for review before a separate profile
update. Increment the profile revision, link the new calibration
digest and preserve the original global clock policy for fields that
were not recaptured.
